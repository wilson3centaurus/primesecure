# Device media: metadata, covers, requested originals

- Telemetry is metadata only: at most 5,000 entries and 24 previews, at most 120px/25KB each. PDF first pages, video frames and embedded audio art reuse `LocalMediaCovers`; no synthetic book covers. Unsupported/missing/budget-limited previews are labelled. Identical inventory uses `device_file_snapshot_touch`, not another full snapshot.
- Only shared student-accessible storage is scanned; Android directories, hidden paths, canonical escapes and protected app/system paths are excluded. USB respects the school restriction.
- `request_device_file` checks the signed-in school manager, derives metadata from the cached device inventory, and records who requested which file. Decimal 500 MB (500,000,000 bytes) maximum original, matching the server's global storage limit; 100 requests/device/day, 10 simultaneous pending requests. Repeated requests reuse the same unexpired transfer.
- `retrieve_file` carries only `request_id`. Native helper obtains a server ticket, checks local canonical path, current enrollment and exact size/mtime before/after upload. Notifications must be visibly enabled. The original streams directly to private `device-file-originals/<school>/<device>/<request>/original`; it never passes through a Next.js action.
- Only managers of that school can read completed, unexpired originals. Teachers, devices and anonymous callers cannot download them. Devices can only insert into their exact pending request, not overwrite or list originals. Attachment URLs last at most 60 seconds, bounded by the request's expiry.
- Access expires 24h after request creation, including unfinished uploads. Audit records remain, with no original contents. Deleting a device/school revokes access immediately but preserves the cleanup pointer (foreign keys set null rather than cascading the request away). Storage API cleanup also removes partial/unfinalized objects bound to expired requests; it never deletes metadata rows directly from `storage.objects`.

## Integration / release gates (no production changes made here)

1. Apply `20261018232514_device_media_on_demand.sql` with the other approved migrations. It augments rather than replaces the current command-type constraint. Any later migration rebuilding that constraint must preserve `retrieve_file`.
2. CommandRunner owner must add: `"retrieve_file" -> DeviceFileTransfer(context, store).upload(payload)`.
3. Deploy/build the updated APK as well as dashboard. Old agents will report unsupported command; cached metadata remains usable.
4. Cleanup is NOT configured by this slice. The parent release task owns `tools/maintenance/resource-retention.py`, its `.cron`, and `apply-library-release.py --install-retention`: select expired `device_file_transfers` with `cleaned_at is null`, remove their objects through the Storage API, and only then mark `cleaned_at`; retain the request rows for audit. Run hourly (daily is acceptable), retry failures, monitor backlog, and verify actual scheduled deletion. This VPS route does not require Vercel `CRON_SECRET` or a Vercel service-role key. An optional equivalent dashboard endpoint, `GET /api/device-file-cleanup`, is included: it requires a server-only service-role key plus a strong `CRON_SECRET` (32+ characters) as bearer authorization; it processes up to 1,000 expired requests/run. Until either scheduler is configured and tested, access expiry works but physical blob deletion is NOT automatic. Never delete rows directly from `storage.objects`.
5. Physical tests still required: real PDF/video/album art on PrimeOS, offline queued request, visible notice, 300–500 MB interrupted transfer/token refresh, school isolation via Storage API, 60s link expiry, and scheduled deletion of completed plus abandoned uploads.

The cached inventory may be stale or bounded. An original absent from it must first appear in a new telemetry scan. A changed file is rejected; refresh then request its new version. No camera, private-screen, Google-account, or student-library changes are part of this slice.
